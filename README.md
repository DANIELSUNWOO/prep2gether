# Prep2gether

> 취준생이 취업 정보를 나누고, 스터디를 모집·운영하며, 전문가에게 유료로 1:1 상담을 받는 커뮤니티 플랫폼입니다.

| 데이터 모델 | [docs/design/erd.md](./docs/design/erd.md) · [docs/sql/00_ddl.sql](./docs/sql/00_ddl.sql) |

### 핵심 사용자 흐름

```text
회원가입(이메일 인증) → 로그인 → 게시판·스터디 활동
                                   └→ 구독 결제(PortOne) → 전문가 1:1 상담
```

## 핵심 기능

### 회원 인증 · 계정

- 이메일 인증 후 가입하고, 일반/카카오·구글·네이버 소셜 로그인으로 접속합니다. 동일 이메일이면 소셜·일반 계정이 자동 통합됩니다.
- JWT(Access) + Refresh Token(HttpOnly 쿠키)을 발급하고, 로그인 5회 실패 시 계정을 잠급니다. 비밀번호는 BCrypt로 해싱합니다.
- 만료·불일치 인증코드, 잠금 임계값, 계정 통합 경로를 서비스 계층 테스트로 검증했습니다.

### 게시판

- 카테고리별로 글을 쓰고, 검색·페이징으로 조회하며, 댓글을 남깁니다.
- 삭제는 `@SoftDelete`로 처리하고 연관 이미지·댓글을 함께 정리합니다.
- 작성자 외 수정/삭제 거부, 존재하지 않는 게시글을 테스트했습니다.

### 스터디

- 스터디를 개설·검색하고 신청하며, 가입 멤버만 스터디 전용 게시판을 이용합니다.
- 미구독자는 개설+참여 합산 2개(`FREE_TIER_STUDY_LIMIT`)로 제한하고 구독자는 무제한이며, 방장 위임·정원·중복 가입을 서비스 계층에서 검증합니다.
- 가입 한도 초과, 방장 위임 없이 탈퇴, 정원 초과 시나리오를 테스트했습니다.


### 전문가 상담

- 구독자는 승인된 전문가에게 1:1 상담 스레드를 열고 대화합니다.
- 스레드 개설 시 요청자 행에 **비관적 락**(`PESSIMISTIC_WRITE`)을 걸어 동일 전문가 중복·개수(`MAX_OPEN_THREADS = 5`) 제한을 직렬화하고, 전문가 첫 답변에서 상태를 `PENDING → ANSWERED`로 전이하며 메일로 알립니다.
- 비구독자 차단, 중복 스레드, 개수 초과, 종료된 스레드 작성 차단을 테스트했습니다.

### 이미지 첨부 (공통)

- 게시글, 스터디, 스터디 게시판, 전문가 상담 메시지에 이미지를 첨부할 수 있습니다.
- 공통 `FileStorageService`(S3FileStorageService)로 `multipart` 요청을 받아 **AWS S3**에 업로드하고, 각 도메인은 `PostImage`/`StudyImage`/`StudyPostImage`/`FeedbackMessageImage`로 원본 엔티티와 연결합니다.
- 원본(게시글 등)이 소프트 삭제되면 연관 이미지도 함께 정리합니다.

### 신고 (공통)

- 게시글·댓글·스터디 게시글·스터디 게시글 댓글·전문가 상담(`ReportTargetType`: POST/COMMENT/STUDY_POST/STUDY_POST_COMMENT/FEEDBACK)에 공통으로 신고를 남길 수 있습니다.
- 본인 대상·중복 신고를 서비스 계층에서 막고, 관리자는 신고 목록을 상태별로 조회해 승인/반려 처리합니다.
- 본인·중복 신고 방지, 존재하지 않는 대상 신고를 테스트했습니다.

### 유료구독 결제 (PortOne V2, 팀 공통)

- 카드를 등록하고 정기결제로 구독하면 전문가 상담이 열리며, 매달 자동 갱신되고 실패 시 재시도할 수 있습니다.
- PortOne 빌링키를 **AES/GCM으로 암호화**해 저장하고, 결제는 PG 응답이 아니라 **결제 단건 재조회 6단계 검증**(상태·상점·채널·환경·금액·통화)으로 확정합니다. 매일 새벽 4시 스케줄러가 만료 임박·연체 구독을 청구하고, 웹훅은 `WebhookEvent` 기록으로 멱등 처리합니다.
- 검증 실패 시 `FAILED` 기록·구독 미반영, 중복 구독 방지, 연체(PAST_DUE) 재시도·쿨다운, 자동 갱신/만료 정리를 단위 테스트로 확인했습니다.

### 관리자

- 게시글·댓글·스터디·상담을 소프트 삭제로 관리하고, 신고 목록을 상태별로 조회해 승인/반려하며, 계정 상태(ACTIVE ↔ SUSPENDED)를 변경합니다.

## 아키텍처

```text
Browser ──HTTP──▶ Nginx (EC2)
                     ├──▶ React (정적 파일)
                     └──▶ Spring Boot API ──▶ MySQL      (영속 데이터)
                                            ├──▶ AWS S3   (이미지)
                                            ├──▶ PortOne  (결제/빌링키/웹훅)
                                            └──▶ Gmail SMTP (이메일 인증)
```

Backend는 `controller → service → repository`로 계층을 나누고, 요청·응답에는 Entity 대신 DTO를 사용하며, 공통 응답은 `ApiResponse` 포맷으로 통일합니다.

## 주요 기술 의사결정

### 결제 성공을 PG 응답이 아닌 "단건 재조회"로 판정

- 상황: PortOne 결제창/빌링키 청구의 즉시 응답은 위·변조 가능성이 있어 그대로 신뢰하기 어렵습니다.
- 결정: 응답과 별개로 결제를 재조회해 상태·상점·채널·환경(TEST/LIVE)·금액·통화 6가지를 대조하고, 하나라도 어긋나면 `FAILED`로 기록한 뒤 구독 반영을 거부합니다.
- 결과·한계: 환경 오반영·금액 변조를 차단했습니다. 완료 처리는 멱등하게 설계해 재호출에도 안전하며, 환불은 API 대신 해지(다음 회차 중단)로 처리합니다.

### 결제 실패를 예외가 아닌 boolean으로 처리

- 상황: 카드사 거절처럼 "정상적으로 실패"할 수 있는 경우 예외를 던지면 트랜잭션이 롤백되어 방금 증가시킨 실패 횟수(`retry_count`)까지 사라집니다.
- 결정: 청구 결과를 boolean으로 반환하고, 실패 시 `PAST_DUE`·재시도 횟수 증가를 같은 트랜잭션에서 남깁니다. 자동 갱신 스케줄러는 건별로 트랜잭션을 열어 한 사용자의 실패가 다른 사용자 처리를 되돌리지 않게 했습니다.
- 결과·한계: 실패 이력과 유예 상태가 정확히 남습니다. 사용자 수동 재시도는 자동 재시도 횟수를 소진하지 않도록 모드를 분리했습니다.

### 탈퇴한 유저의 JWT 토큰이 아직 유효기간 내에 남아있으면 어떻게 처리하나?

- 상황:유저가 회원탈퇴하면 status = WITHDRAWN으로 소프트 삭제 처리되지만, 탈퇴 전에 발급받은 access token은 만료시간(1시간)까지 여전히 유효함
, JWT는 stateless 구조라 서버가 이미 발급한 토큰을 즉시 강제로 무효화할 방법이 없음
, 이 상태로 API를 호출하면 JwtAuthenticationFilter가 서명·만료 검증만으로는 통과시켜버릴 수 있음
- 결정: User를 하드 삭제하지 않고 소프트 삭제(status 변경)하는 정책을 쓰고 있으므로, "유저가 DB에 아예 없는 경우"와 "유저는 있지만 탈퇴 상태인 경우"를 구분해서 처리하기로 함, 필터는 인증 여부(신원 확인)만 판단하고, 실제 이용 가능 여부(탈퇴/정지 등 상태 체크)는 각 서비스 로직이 책임지도록 역할을 분리하기로 함
- 결과·한계: JwtAuthenticationFilter는 존재하지 않는 유저만 걸러내고, 탈퇴 여부 자체는 각 API의 checkAccountActive()에서 명시적으로 차단하는 구조라, 이 체크를 거치지 않는 API는 access token이 만료(최대 1시간)되기 전까지 탈퇴 유저의 접근이 완전히 막히지는 않는다는 한계가 있습니다.

### 메일 발송이 핵심 트랜잭션과 응답 속도에 영향을 주지 않게 분리

- 상황: 상담 답변 등록, 전문가 승인/반려, 구독 시작/취소처럼 DB 저장과 이메일 알림이 함께 일어나는 로직에서, 메일 발송을 동기로 처리하면 메일 서버 응답 지연이 API 응답 속도에 그대로 반영됩니다. 또한 트랜잭션 커밋 전에 메일을 보내면 아직 확정되지 않은 데이터를 기준으로 알림을 보내게 되고, 메일 발송 실패가 예외로 전파되면 정상 저장된 비즈니스 데이터까지 롤백될 위험이 있습니다.
- 결정: 두 단계로 분리했습니다. AfterCommitExecutor로 메일 발송 호출 자체를 트랜잭션 커밋 이후로 미루고(TransactionSynchronizationManager에 콜백 등록), EmailService의 발송 메서드에는 @Async를 붙여 실제 메일 전송이 별도 스레드에서 실행되도록 했습니다. 메일 전송 실패는 EmailService 내부에서 로그만 남기고 호출자에게 예외를 전파하지 않습니다.
- 결과·한계: 상담 답변 저장(FeedbackService), 전문가 승인/반려(ExpertProfileService), 구독 시작/취소(SubscriptionService) 전반에 동일한 패턴을 적용해, 메일 지연이 응답 속도에 영향을 주지 않고 메일 실패가 핵심 로직을 롤백시키지도 않습니다. 다만 메일 발송이 실패해도 사용자나 운영자에게 알릴 별도 수단이 없어 실패를 인지하지 못할 수 있다는 한계가 있고, 전문가 도메인만의 고유 로직이 아니라 결제·전문가 승인 등 서비스 전반에 적용된 공통 패턴입니다.

### 신고를 FK가 아닌 논리적(다형) 참조로 통합

- 상황: 신고 대상이 게시글·댓글·스터디게시글·스터디댓글·전문가 상담 5종인데, 대상마다 신고 기능을 따로 두면 중복이고 한 컬럼으로 다섯 테이블을 동시에 FK로 잇는 것도 불가능합니다.
- 결정: `target_type`(enum)과 `target_id`로 대상을 가리키는 단일 `Report` 테이블·단일 API(`POST /api/reports`)로 통합했습니다. DB FK 대신 애플리케이션이 타입별 리포지토리로 대상 존재를 검증(`switch`)하고, 중복 신고는 "동일 신고자·대상의 `PENDING` 신고 존재" 기준으로 막으며, 비공개인 상담(`FEEDBACK`)만 스레드 참여자로 신고 권한을 제한합니다.
- 결과·한계: 새로운 신고 대상이 생겨도 enum 추가만으로 확장됩니다. 대신 참조 무결성을 DB가 아닌 애플리케이션이 책임지므로, 대상이 이미 삭제된 경우 관리자 목록 조회에서 "삭제된 게시글입니다"처럼 타입별 방어 문구로 대체합니다.

### 게시글 수정·삭제 권한을 정규 경로와 관리자 경로로 분리

- 상황: 관리자도 타인의 글을 삭제할 수 있어야 하는데, 정규 수정/삭제 API에 `role == ADMIN` 예외를 넣으면 "작성자 본인만"이라는 규칙에 구멍이 생기고 권한 로직이 도메인마다 흩어집니다.
- 결정: 정규 경로(`PUT`·`DELETE /api/posts/{id}`)는 `isOwner()`만 검사해 작성자 본인으로 한정하고, 관리자 강제 삭제는 `/api/admin/**` 전용 경로로 분리했습니다. 실제 삭제 로직(딸린 댓글·이미지 정리)은 `deletePostCascade` 한 메서드로 모아 작성자 삭제와 관리자 삭제가 공유합니다.
- 결과·한계: 정규 경로는 항상 본인, 관리자 권한은 별도 경로로 명확히 갈립니다. 다만 관리자에게는 삭제(숨김)만 열어 두고 타인 글 수정 기능은 두지 않았습니다.

### 방장 탈퇴를 삭제가 아니라 "위임 강제"로 설계

- 상황: 스터디에 다른 멤버가 남아 있는데도 방장이 그냥 탈퇴해버리면, 남은 멤버들의 게시글·댓글은 그대로인데 스터디를 대표하는 방장만 사라지는 상태가 됩니다. 정원·게시글 고정·강퇴 같은 방장 권한을 아무도 행사할 수 없는 스터디가 만들어지는 셈입니다.
- 결정: `leaveStudy`에서 탈퇴자가 방장인지 먼저 확인하고, 남은 멤버가 없을 때(본인 1명)만 `deleteStudyCascade`로 스터디 자체를 정리합니다. 멤버가 남아 있으면 곧바로 탈퇴시키지 않고 `STUDY_LEADER_MUST_DELEGATE` 예외로 막아, 반드시 `delegateLeader`로 다른 멤버에게 방장을 위임한 뒤에만 탈퇴할 수 있게 했습니다. 본인에게 위임하는 것도 별도로 막았습니다.
- 결과·한계: 멤버가 남아 있는 스터디가 방장 없는 상태로 방치되는 경우를 원천적으로 없앴습니다. 다만 후임 방장 지정은 전적으로 기존 방장의 선택에 맡겨져 있어, 방장이 위임 없이 잠수 타면 다른 멤버는 스스로 방장을 승계할 방법이 없고 관리자의 강제 삭제로만 정리할 수 있다는 한계가 있습니다.

## Troubleshooting

### 소프트삭제 도입 후 LAZY 연관 로딩 실패

- 문제: `Post`에 `@SoftDelete`를 적용하자, 이를 `@ManyToOne(LAZY)`로 참조하던 `Comment`·`PostImage`에서 연관 로딩 오류가 발생했습니다.
- 조사: Hibernate 6.4+에서는 `@SoftDelete`가 걸린 엔티티를 지연(LAZY) 프록시로 참조할 수 없다는 제약을 확인했습니다.
- 해결·검증: `Comment`·`PostImage`의 `Post` 참조를 `EAGER`로 변경해 조회를 정상화하고, 소프트삭제된 게시글·댓글이 목록 조회에서 자동 제외되는지 테스트로 확인했습니다.

### 상담 메시지·목록 조회에서의 N+1 문제

- 문제: 상담 메시지 목록 조회(getMessages)에서 메시지마다 첨부 이미지를 개별 쿼리로 가져오고 있어, 메시지 개수만큼 쿼리가 추가로 발생했습니다. 동시에 내 문의 목록/받은 문의 목록 조회에서도 요청자 닉네임·전문가 이름을 표시하려고 연관 엔티티를 지연 로딩하면서 같은 문제가 겹쳐 있었습니다.
- 조사: 쿼리 로그로 메시지 이미지 조회가 메시지 수만큼 반복 실행되는 것을 확인했고, 목록 조회에서도 requester·expertProfile.user가 LAZY라 페이지 크기만큼 추가 쿼리가 나가는 것을 확인했습니다. 두 연관관계 모두 @ManyToOne(다:1)이라 JOIN FETCH를 페이지네이션과 함께 써도 결과 row 수가 늘지 않아 안전하다는 것도 같이 확인했습니다.
- 해결·검증: 이미지 조회는 메시지 ID 목록을 IN 절로 한 번에 가져온 뒤 messageId 기준으로 그룹핑하는 배치 조회로 바꾸고, 목록 조회 쿼리는 JOIN FETCH로 requester/expertProfile.user를 함께 가져오도록 수정했습니다. 수정 후 쿼리 로그에서 반복 쿼리가 사라지고, 페이지네이션 결과 개수가 그대로 유지되는지 테스트로 확인했습니다.

### 게시글 삭제 시 딸린 댓글·이미지가 함께 정리되지 않던 문제

- 문제: `@SoftDelete`는 삭제 플래그만 바꿀 뿐 연관된 댓글·이미지를 자동으로 정리하지 않습니다. 게시글 삭제를 `postRepository.delete(post)` 한 줄로만 처리하던 초기 구현에서는 게시글만 숨겨지고 딸린 댓글·이미지 레코드가 그대로 남았습니다.
- 조사: 소프트 삭제는 DB의 `ON DELETE CASCADE`나 JPA `cascade = REMOVE`가 개입하지 않는 경로라, 연관 데이터 정리를 애플리케이션이 직접 수행해야 함을 확인했습니다.
- 해결·검증: 삭제 로직을 `deletePostCascade`로 모아 댓글·이미지를 먼저 정리한 뒤 게시글을 삭제하고, 작성자 삭제(`deletePost`)와 관리자 강제 삭제(`adminDeletePost`)가 이 메서드를 공유하도록 했습니다. 삭제 시 딸린 댓글·이미지가 함께 정리되도록 하고, 기존 서비스 테스트로 회귀가 없음을 확인했습니다.

### 게시글 목록 조회의 N+1 (작성자 · 이미지)

- 문제: 게시글 목록(`getPosts`/`getMyPosts`) 변환 시 게시글마다 작성자 닉네임(`post.getUser()`, `@ManyToOne(LAZY)`)과 첨부 이미지(`getImageUrls(postId)`)를 개별 조회하면서, 페이지 크기만큼 작성자 조회 + 이미지 조회 쿼리가 추가로 발생했습니다(한 페이지 10건이면 목록 1 + 작성자 10 + 이미지 10).
- 조사: `searchPosts`가 작성자를 함께 조회하지 않는 것을 확인했습니다. 작성자는 `@ManyToOne`이라 `JOIN FETCH`를 페이징과 함께 써도 결과 row가 늘지 않아 안전한 반면, 이미지는 일대다 컬렉션이라 `JOIN FETCH` + 페이징을 함께 쓰면 row가 뻥튀기돼 페이지 개수가 깨진다는 점을 확인했습니다.
- 해결·검증: 작성자는 목록 쿼리에 `JOIN FETCH`로 함께 가져오고(그에 맞춰 `countQuery`를 분리), 이미지는 게시글 ID 목록을 `IN` 절로 한 번에 조회한 뒤 `postId` 기준으로 그룹핑하는 배치 조회로 바꿨습니다. 수정 후 목록 조회가 게시글 수와 무관하게 고정된 쿼리 수(목록 1 + 이미지 1)로 처리되며, 기존 서비스 테스트로 결과·페이지 개수 회귀가 없음을 확인했습니다.

### 스터디 가입 시 정원 체크의 동시성 문제

- 문제: `joinStudy`가 현재 인원(`countByStudyId`)을 조회해 정원과 비교한 뒤 별도의 락 없이 `StudyMember`를 저장하고 있었습니다. 정원이 1자리 남은 상태에서 여러 요청이 동시에 들어오면 모두 같은 인원 수를 읽고 통과해버려, 정원을 초과한 채로 저장될 수 있는 구조였습니다.
- 조사: 이미 전문가 상담 스레드 개설에 적용한 것과 같은 패턴 — "조회 후 판단(check-then-act)"만으로는 동시 요청 사이의 경합을 막을 수 없다는 점을 확인했습니다. `Study` 조회 시점에 락이 전혀 걸리지 않아, 인원 체크와 저장 사이에 다른 요청이 끼어들 여지가 있었습니다.
- 해결·검증: `joinStudy`에서 대상 `Study` 행에 **비관적 락**(`PESSIMISTIC_WRITE`)을 걸어 동일 스터디에 대한 가입 요청을 직렬화하도록 수정했습니다. 정원이 1자리 남은 스터디에 동시 가입 요청을 보내는 시나리오로 정원 초과 저장이 발생하지 않는지 테스트로 확인했습니다.
